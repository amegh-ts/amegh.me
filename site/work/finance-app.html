Why I built it

The problemManual logging stops

I built Finance App to track my own daily spending. It started as a side project, something to think about after long days on payment systems at work, and grew into a web app with an Android companion, live updates and automatic import from bank SMS.

Most expense apps fail for one reason: you stop entering expenses. I wanted the boring part, logging each card spend or EMI, to happen on its own.

What it does

FeaturesMoney, at a glance
  • Money in and out: income, expenses and transfers, with categories and tags.
  • Monthly budgets with alert thresholds, so overspending shows up before the month ends.
  • Loans with repayment history, and savings goals.
  • Analytics across six months.
  • Live balances over Socket.IO, and web push alerts for budgets and due dates.
  • Installable as a PWA.
  • An Android companion that captures bank SMS on the phone, with a Review tab for anything it isn't sure about.

How the SMS import works

ArchitecturePhone, n8n, server

A bank message comes in and a correct transaction appears. Getting there safely took most of the design work.

  1. A message arrives. The Android app captures bank SMS on the phone. I can also forward a message to my n8n "Expense Assistant" on WhatsApp or Telegram.
  2. n8n spots bank messages. It checks for phrases such as "Credit Card ending" or "loan account". Anything else goes through the assistant's normal flow.
  3. The server does all the parsing. n8n only forwards the raw text to one endpoint, POST /api/integrations/sms. Parsers on the server handle EMI messages, card spends and the phrasing common to Indian banks and UPI.
  4. It matches the message to my data: the last four digits to an account or credit card, a loan account number to the right loan.
  5. It never guesses. A message it can't match with confidence goes to a review inbox instead of becoming a wrong transaction. I get a push notification and fix it in a tap.
  6. It never counts twice. Each message's normalised text is hashed and stored, so the same SMS captured by the phone and forwarded through n8n creates one transaction, not two.
  7. Phone capture wins. When the same spend arrives from several sources, the phone's SMS capture beats a forwarded message, which beats a bank-app notification.

When a bank uses a new message format, I add its trigger phrase in n8n and a parser on the server. Every import starts as unreviewed, and each correction is kept as a record.

The hard parts

LessonsWhat took longest

Calculation logic

Budgets, loan repayments, savings goals and running balances all depend on the same transactions. One edit ripples through all of them, and with live updates the numbers have to be right the moment they change.

Adding a phone app to a web app

The web app came first. Adding the Android companion meant reshaping the APIs and data flow so both share one backend, without breaking what already worked.

Learning Flutter

I'd never built in Flutter. I learned it while building the companion, using AI tools to get up to speed. It was the steepest new skill in the project.

What I learned

TakeawaysFor any automation
  • Queue when unsure, don't guess. A review inbox is cheaper than a wrong balance.
  • Deduplicate on content. The same event will arrive more than once, from more than one place.
  • AI tools make a new platform approachable, but the architecture decisions are still yours to own.
